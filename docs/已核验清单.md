## 七、牌面分辨率：3 倍屏略软，但**决定不提**

**现状**：牌面图 140×196，金花里显示 136rpx（= 68pt）。
在 3 倍屏上需要 204 像素，而图只有 140 —— **等效 0.69 倍**，略软。

**算过提分辨率的账**（2026-11-03）：

| 方案 | 体积 | 是否可行 |
|---|---|---|
| 提到 2 倍（280×392） | 206 → **825 KB**（+619） | **超限**（1680 + 619 = 2299 > 2048）|
| 提到 1.5 倍（210×294） | +258 KB → 1938 KB | 可行，但只是**插值放大**，不增加真细节 |
| 保持现状 | 206 KB | ✓ |

**决定：保持现状。**

理由：1.5 倍是"用 258KB 换一点抗锯齿"，而**真细节需要更高分辨率的原始素材**。
仓库里没有 Kenney 牌的源 SVG（当初只取了渲染好的 PNG）。

**如果以后真觉得糊**，正确的做法是**重新找源素材**（Kenney Boardgame Pack 的 SVG 或 2x PNG），
而不是拿现有图插值放大 —— 后者是被 `docs/音效时长对照.md` 里那条
「换素材要重新算派生值」反过来的同一个道理：**放大不是换源**。

⚠️ 顺带：**这个"略软"在渲染图上看不出来**（渲染器是 1:1 出图）。
所以它是"真机才能察觉"的那一类 —— 和声音好不好听、动画跟不跟手一样，
**我只能指出它可能软，没法证明它看起来能不能接受。**

## 八、头像 8 色对色盲不友好 —— 但**不改**，因为座位号已经解决识别

**算了一遍**（红绿色盲模拟后按感知亮度排序）：

    红 0.401   黄 0.509   黄绿 0.397   绿 0.279
    青 0.296   蓝 0.219   紫  0.293    品红 0.413

**问题**：`红(0.401) ≈ 黄绿(0.397)`、`绿(0.279) ≈ 紫(0.293) ≈ 青(0.296)` ——
红绿色盲（男性约 8%）在这三对之间会混。

### 为什么决定不改

**每个头像旁边都有大号座位号 1~8**。色盲用户靠**数字**识别自己和别人，
颜色只是"扫一眼找到我"的辅助。

而"拉大亮度差"试了三版都失败：

| 方案 | 最小相邻亮度差 |
|---|---|
| 色相均匀 + 亮度阶梯（HLS 的 L） | 0.020 |
| 亮度主导（HLS 的 L） | 0.009 |

**根因**：`colorsys.hls_to_rgb` 里的 `L` 不是**感知亮度** ——
黄色和蓝色取同一个 `L`，感知亮度能差 3 倍。
要真正拉开，得在 LAB 空间里按目标亮度反解色相，或者干脆用灰度。

**而收益很小**：识别已经有数字兜底；而灰度会让 8 个头像看起来很沉闷。

⚠️ 这不是"没想到"，是**权衡后选择不做** —— 记在这里，免得下次重新算一遍。

## 九、「被罚」只有声音+震动，没有视觉动画 —— 试过，风险大于收益

**现状**（`feedback.js` 的 `penalized`）：

    animMs: 360, sfx: 'failDrop', sfx2: 'glassClink'(+260ms), haptic: 'long', vol: 1

**声音是两声**（下坠 + 碰杯）、**震动是 long** —— 这两层都很到位。
而 `animMs: 360` 这个数字**没有任何视觉在用**（模板里没有对应的 class）。

### 想加"落下 + 回弹"，但有两个坑

**坑一：轮询会让 CSS animation 反复重播。**
AGENTS.md 记过：结算页每 1.5 秒 setData 一次，`wx:for` 会重建节点 →
CSS `animation` 每次重建都重播。金花发牌动画就是因此改用 `transition`。

**坑二：`transition` 也需要"值变化"才触发。**
而 `.loserbox` 的内容（`{{result.loserName}} 喝 1 杯`）在结算后是**不变的** ——
没有值变化，transition 不会跑。

**要让它跑一次，得在 `decorate` 里加一个"刚结算"的时间戳标记** ——
而那是给一个 360ms 的动画引入一个**跨 1.5 秒轮询都存在的状态**，
出错时的表现是"每 1.5 秒弹一下"——**比没有动画糟得多**。

### 所以不做

**"被罚"这件事的强度，主要靠声音和震动就够了** ——
失败音 + 260ms 后的碰杯音 + long 震动，而 `.loserbox` 是 44rpx 的大字
（专门为"隔着桌子能读"调过）。

**动画能让它更好，但代价是"可能每 1.5 秒闪一次"的风险。**

⚠️ 这不是"没想到"，是**权衡后选择不做**。如果以后真要加，
正确做法是"结算瞬间播一次音频 + 用一个只存在一次的标记"，而**不是靠 CSS 自己动**。

## 十、「查表 API」的静默失败风险 —— 逐个核过

**这类 API 的共同形态**：

    const x = TABLE[key]
    if (!x) return          ← 拼错一个字，这个错误就永远不暴露

**它不会崩，只会安静地什么都不做。** 而"什么都没发生"在小程序里
和"本来就没事发生"是一模一样的 —— 用户不会报，我也看不到。

| API | 未知 key 时 | 兜底 | 调用点判空 | 断言 |
|---|---|---|---|---|
| `feedback.fire(key)` | `console.warn` + return | 无 | — | ✓ 21 个白名单 |
| `sfx.play(key)` | **直接 return**（连 warn 都没有）| 无 | — | ✓ 33 个白名单 |
| `games.gameOf(id)` | 返回 `null` | 无 | ✓ 三处都判了 | — |
| `decks.deckOf(key)` | **回退 `FRIENDS`** | ✓ 有 | 不需要 | — |
| `icons.dataUri(k)` | 空串 | 无 | — | ✓ 已有（③e-3）|

### 真实案例

`feedback.fire(iLost ? 'lose' : 'win')` —— `'lose'` 不在表里（表里叫 `penalized`），
于是**比大小输了的时候一声不响、也不震**。

而抓住它纯属运气：查 `celebrate()` 的调用上下文时，顺手看到了下一行。

**所以才有那两条白名单断言。**

### 新增这类 API 时的清单

1. **未知 key 时返回什么**？`null`（明确）好过 `undefined`（容易混进计算）
2. **要不要兜底**？`deckOf` 用 `|| FRIENDS`（永远有值）—— 适合"回退是合理行为"的场合
3. **调用点多不多**？少于 5 处就逐个判空；多了就写白名单断言
4. **名字是常量还是手写**？手写的字符串字面量最容易拼错 —— **优先用常量**

⚠️ 第 4 条本项目还没做：`fire('win')`、`sfx.play('toggleOn')` 这些**全是手写字面量**。
改成常量能彻底消灭拼错，但改动面太大（30+ 处），**暂时靠断言兜住**。

## 十一、「容器缩了、absolute 子元素没缩」—— 16 个逐个查过，只有 1 个要改

**起因**：转盘容器缩到 464rpx，而圆盘 `.ws-disc`（absolute + 写死 560rpx）没缩 →
**溢出容器、压住标题**。已修。

于是把 room.wxss 里**所有"有尺寸的 absolute 元素"列出来逐个查**（16 个）：

| 类 | 性质 | 要不要跟着缩 |
|---|---|---|
| `.ws-disc` | 转盘圆盘 | **要**（已修）|
| `.ws-hub` | 转盘中心按钮 | 不要 —— 它是"按钮"，48px 在任何屏上都是合适尺寸 |
| `.cs-cup` | 骰盅本体 | 要（已有 compact 规则）|
| `.cs-dice` | 盅里的骰子区（306rpx）| **不要** —— 见下 |
| `.cs-felt-img` `.cs-prop` `.cs-spot` | 桌布 / 道具 / 光斑 | 装饰层，`width: 100%` 或纯装饰 |
| `.cf` | 撒花粒子 | 装饰 |
| `.eh-glow` `.oh-glow` `.cd-glow` | 光晕 | 装饰 |
| `.ws-pointer` | 指针（无 width）| — |

### 为什么 `.cs-dice` 不用缩（这一条最值得记）

它宽 **306rpx**，而紧凑态骰盅只有 **180rpx** —— **骰子区比盅还宽一倍**。

**看着像 bug，其实是设计**：骰盅是"扣着"的，**骰子故意从盅两侧露出一部分**
（`.cs-dice` 里 5 颗骰子横向排开，两端超出盅的轮廓）。

这是"盅里有东西"的视觉线索 —— 而如果把它缩到和盅一样宽，
**盅看起来就是空的**，那种"摇完了、里面有骰子"的实感就没了。

⚠️ 判断依据不是"数值超了就该改"，而是**看渲染图确认它是不是有意为之**。
   这一条我查了图才敢下结论。

### 所以真正的判据

**"容器缩了子元素没缩"只在一种情况下是 bug：子元素的尺寸依赖容器的语义尺寸。**
  · `.ws-disc` 就是"圆的盘"，容器多大它该多大 → 要缩
  · `.cs-dice` 是"故意溢出的骰子" → 溢出是它的功能

**而这个区别只有看图才能分辨** —— 纯看 CSS 数值（306 > 180）会得出相反的结论。

## 十二、小屏（504pt）上「要滚一点」是设计，不是 bug

**实测**（拼最小 DOM 测 `.gamepage` 的 `scrollHeight`）：

    内容高度 529px  /  视口 504px  →  超出 25px

**25px ≈ 一行文字的高度** —— 也就是说小屏上绝大多数内容在首屏内，
**只有最后一两个元素要滑一下**。

### 这和"布局崩了"的区别

| 现象 | 严重程度 | 怎么区分 |
|---|---|---|
| 内容比视口高 25px，能滚 | **正常** | `scrollHeight - clientHeight` 很小，且 `.gamepage` 没有 `overflow: hidden` |
| 按钮被绝对定位推出屏幕，滚也滚不到 | **严重** | 元素坐标超出文档高度 |
| 元素互相重叠 | **严重** | 渲染图上能看到 |

**它们在小屏截图上一模一样**（都是"底部被切掉"），所以必须用数值区分。

### 判据

**"首屏看不到"和"点不到"是两件事，中间隔着"能不能滚"。**

而"能不能滚"取决于：
  · `.gamepage` 有 `min-height: 100vh`（内容多时能撑开）
  · **没有** `overflow: hidden`（有的话就再也滚不动）

这两条都有断言锁（`test-contract.js`）。

⚠️ 所以以后再看到"小屏底部被切"，**先量数值再判断** ——
不要一看到截断就去缩元素，那可能把一个本来就对的布局改坏。

## 十三、规则弹层的长文本「看起来被裁」—— 查了两层，仍无法定性

**现象**：转盘规则弹层（4 条）里，第 1 条的长句右侧看起来超出屏幕，而第二行是完整的。

**查过的**：

| 层 | 结论 |
|---|---|
| CSS | `.ht-t` 是 `display: block` ✓、`.ht-item` 是 `flex` ✓、`.sheet` 是 `width:100%` + `padding: 32rpx` |
| `check-text-overflow.js`（历史） | `.ht-t` 的 `scrollW == width` → **没溢出** |
| 我的复现（视口 500px） | `T_W=445 T_SW=445` → **没溢出** |

**而渲染器的视口是 375px**（`DEVICE.width = 375`），和我的复现（500px）**不是同一个条件** ——
所以那两组数字不能直接比较。

**我能确定的**：
  · 样式本身没有"定死宽度 / nowrap / overflow:hidden"
  · 独立测 `.ht-t` 没溢出

**我不能确定的**：渲染器在 375px 下、弹层嵌套里，是否真的把它裁了。

### ★ 最终结论（2026-11-03 补）：**真机不裁，是渲染器的偏差**

查清了，而且过程中发现了一个**更严重的问题**：

**`check-text-overflow.js` 一直在测 500px 宽的屏。**

原因：它用 `--dump-dom` 模式，而 **`--window-size` 在那个模式下不生效**
（实测：设了 `--window-size=375,812`，元素宽度还是 461px）。
于是它量的元素宽度是 **461px**，而真机是 **375px** ——
**这条断言一直在一个比真机宽 33% 的屏上测"溢不溢出"。**

**修法**：不能靠浏览器视口，改成**在 HTML 里用 CSS 把宽度钉死 375px**
（`html, body { width: 375px !important }`）。

**修完重测**：

    width=352 scrollW=352    ← 375 - 23（边距）
    ✓ 不溢出

**所以**：`.ht-t` 在真机上会**正常换行**，渲染图上的"被裁"是 `--screenshot`
模式下的已知偏差（`render-ui.js` 自己记过同类问题：`display:none` 的规则
在 `--dump-dom` 里生效、而截图里还在，需要 800ms 虚拟时间才一致）。

### 这条的教训比结论本身重要

**"验证工具测的条件"和"产品的真实条件"不一致时，工具会给出一个永远通过的错误结论。**

  · 它测 500px，产品是 375px → **它对"375px 下会不会溢出"这个问题没有任何信息量**
  · 而它一直显示 `✓ 不溢出`，**看起来像验证过了**

这和本项目记过的「分包之后断言只扫 `pages/`（一直绿、什么都没测）」是同一个病。

## 十四、所有「浏览器验证工具」的测量条件逐个审查过

**起因**：`check-text-overflow.js` 一直在测 500px 的屏（真机 375px），
而它显示 `✓ 不溢出` —— **看起来像验证过了，实际什么都没测**。

于是把**所有**用无头 Chrome 的工具逐个过一遍：哪些受这个偏差影响，哪些不受。

| 工具 | 模式 | 测什么 | 受 500px 视口影响？ |
|---|---|---|---|
| `check-text-overflow.js` | `--dump-dom` | **溢出**（`scrollW > width`）| **是** → 已改成 CSS 钉死 375px |
| `check-css-applied.js` | `--dump-dom` | `display` / `white-space` / 绝对宽度 | 否 —— 这些值**不依赖视口** |
| `verify-compact.js` | `--dump-dom` | `display` / `width`（绝对值）| 否 —— 同上 |
| `render-ui.js` | `--screenshot` | 像素 | 否 —— **`--window-size` 在 `--screenshot` 模式下生效** |

### 所以偏差的范围是精确的

**只有"比较元素宽度和容器宽度"这类判断会受影响** —— 因为它的结果依赖容器有多宽。

**而"这个元素的 `display` 是不是 `none`""它的 `width` 是不是 59px"这类判断不受影响** ——
它们的答案和视口宽度无关。

### 这条的通用判据

**造一个"在浏览器里测东西"的工具时，要问：我取的这些值，答案会随视口变化吗？**

  · 会（溢出、可见性、布局是否折行）→ **必须钉死目标尺寸**
  · 不会（计算样式的绝对值）→ 视口无关，可以不管

⚠️ 而 headless Chrome 的 `--dump-dom` 模式下 `--window-size` **不生效**
（实测：设 375 仍得到 461px 的元素宽）——
所以"钉死"必须用 CSS（`html, body { width: 375px !important }`），不能靠命令行参数。
