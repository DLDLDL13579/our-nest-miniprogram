# 第 8 轮调研：第 9 个玩法的选择（2026-11-03）

## 一、先否掉一个"看起来该做"的方向

看机制矩阵，8 个玩法**全是回合制**（你一步我一步），没有需要**同时反应**的。
直觉上"实时抢答"是明显空白 —— 但查完资料后**否掉了**。

来源：[Spaceteam (TechRadar)](https://www.techradar.com/news/the-10-best-smartphone-games-to-play-with-your-family)、
[Pocket Party 的 Reaction](https://www.facebook.com/PocketPartyApp/posts/)、
[Jackbox 同时作答机制](https://en.wikipedia.org/wiki/The_Jackbox_Party_Pack)。

| 反方证据 | 说明 |
|---|---|
| 酒桌是面对面的 | 大家低头抢手机，反而把桌子拆散了 |
| 喝过酒后反应差异大 | 输赢主要由酒量决定，不是判断 |
| **1.5 秒轮询做不到公平** | 实时反应需要低延迟，本项目架构物理上做不到 |
| 铁律① | 手机是桌上道具，实时抢 = 一直点 |

> **结论：方向对（确实缺"同时性"），但形态错。** 要补的是"同时"，
> 不是"实时"—— 可以先各自秘密作答、再一次性揭晓，不需要低延迟。

## 二、真正的空白：8 个玩法全是零和，没有合作

| 机制轴 | 已被哪些玩法占 |
|---|---|
| 隐藏信息 | 大话骰、谁是卧底 |
| 运气 | 比大小、命运转盘、射龙门 |
| 价格/代价 | 梦幻金花（换牌）、射龙门（押注） |
| 信息方向 | 额头牌（反向） |
| 规则变化 | 红黑单双大小 |
| **合作（共同目标）** | **一个都没有** |

酒桌上确实有"一起干一杯"这种合作场景，但**游戏机制层面完全没有**。

## 三、候选：众口一致（名字待定）

### 规则草案

每人先在心里想一个数值（或从给定范围里选一个），
然后全场回答**同一个估计问题**，答案落在**同一区间**才算通过。

- 通过 → 全场一起松口气（不喝）
- 不通过 → 离群最远的人喝

### 为什么它避开了「押谁最接近」的题库坑

**这是本轮最关键的判断。**

| | 押谁最接近 | 众口一致 |
|---|---|---|
| 需要标准答案吗 | **需要**，且必须长期可查证 | **不需要**，只看"大家是否接近" |
| 题库成本 | 收 50 道带出处的数值题，试收命中率 50% | **零** —— 数值来自玩家自己 |

押谁最接近卡在题库上（见 `玩法调研-第6轮-数值题试收.md`），
而这个玩法**根本没有标准答案要查**，所以那个成本不存在。

### 三种形态里选"数字估计"

| 形态 | 优 | 劣 |
|---|---|---|
| 选择题 | 判一致简单 | 像智力问答，酒桌上不够热闹 |
| **数字估计** | 有张力：看谁保守谁激进 | 需要定"多接近算一致" |
| 排序/多选 | 讨论空间大 | N 人排序几乎不可能完全一致 |

### 判据（铁律②）

| 判据 | 是否命中 |
|---|---|
| **秘密信息** | ✓ 各人答案必须先保密，同时揭晓才成立 |
| **仲裁顺序/计时** | ✓ "多接近算一致"必须一处判，各人心里各有一本账 |
| 真随机 | ✗ 不需要 |
| 大量内容库 | ✗ 不需要 |

## 四、必须写死的歧义（不写一定会吵）

1. **多接近算一致？** —— 必须给一个明确的比例（如：最大值与最小值相差不超过 30%）
2. **谁喝？** —— 是离群的那一个人，还是全场一起？建议：**离群最远的那个**
3. **几个人玩才成立？** —— 1 人没有"一致"可言，最少 2 人
4. **数值范围** —— 每轮由服务端定一个范围，避免有人猜 1 有人猜 100 万
5. **题目从哪来？** —— 见下

### 题目来源：不给题库，让规则自己生成

这是本设计最省的一处 —— **不需要收题库**：

- 形态 A：每人先秘密选一个 1~100 的数，然后全场猜"平均数是多少"（经典的猜平均数博弈）
- 形态 B：房主现场报一个题（"这瓶酒还剩多少"），全场输入百分比

⚠️ 形态 A 更干净（零外部依赖），但它其实变成了"猜别人怎么想"，
需要再想清楚它和"合作"的关系 —— **这一条留到下一轮决定**。

## 五、结论（本轮已定，不再是"待定"）

**做形态 B「众口一致」，规则模块已完成并穷举验证。**

### 为什么选 B 不选 A

| | 形态 A 猜平均数 | 形态 B 房主出题 |
|---|---|---|
| 每轮输入次数 | **2 次**（先选数、再猜平均） | **1 次** |
| 手机参与度 | 全程要盯屏 | **题目是口头的，手机只在"交答案"用一次** |
| 违反铁律①吗 | **是** —— 点两次 | 否 |

### 阈值口径：最大值 × 0.30（试过三种，前两种都错）

| 方案 | 0..30 | 70..100 | 问题 |
|---|---|---|---|
| 中点 × 0.3 | 不通过 | 不通过 | 全 0 时算出"阈值 0 却通过"，文案像 bug |
| sqrt(中点) × k | 不通过 | 通过 | "几十"那档永远不过 |
| **最大值 × 0.3 ✓** | 不通过（阈值 9） | 通过（阈值 30） | 无 |

> 关键认识：**小数字题（"几分钟"）依然会不时不通过 —— 这不是 bug。**
> 它逼着玩家在输入前想"别人会填几"，那正是"合作"的来源。
> 不通过才有人喝；全都通过就没有酒桌张力了。

### 一条被实测推翻的"设计理由"

我原本在注释里写"必须用中位数，因为平均数会被离群者拉偏"。

**穷举验证后是错的**：4 个点、步长 5、0..60 的约 1.8 万组组合里，
中位数法和平均数法选出的离群者 **100% 相同（0 组不同）**。

原因：取"绝对值最大"时，只要中心落在 [第二小, 第二大] 之间，答案就永远是同一端，
而平均和中位都落在这个区间。

代码里保留中位数（更符合直觉、也能应对将来改成"按符号判离群"），
但**测试注释里如实写明了这条断言测不了那个错** —— 把测不了的东西写成能测是自欺。
