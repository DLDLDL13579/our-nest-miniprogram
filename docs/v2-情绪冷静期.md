# v2 · 情绪与冷静期

> 2026-09-24 编写。这是 v2 唯一的功能项，也是 README「下一步做什么」里挂了两轮的那一项。
> **动手前做了调研**（Gottman 研究所 + 临床实践），有四条发现直接改进了设计 —— 见第二节。

---

## 一、为什么做这个

### 定位

**吵架时的「暂停键」，和好后的「复盘本」。**

### 洞察

吵架真正伤人的不是分歧本身，是**上头时说的那些话**。
人在情绪里说的话，十句有八句不是本意，但说出去就收不回来了。

所以这个功能要解决的不是「帮你们解决问题」，而是三件更小、但更实际的事：

1. **上头时能停下来** —— 给一个仪式感的动作，让双方都知道「我们现在需要缓一缓」
2. **缓下来之后各自想清楚** —— 写感受时不被对方的话带偏（这是双盲在这里的真正价值）
3. **和好之后留下点什么** —— 把这次的经验变成下次的默契，而不是白吵一场

### 一个关键判断：双盲在这里才是刚需

「每日一题」的双盲是为了制造悬念，很弱 —— 所以它被否掉了（见 AGENTS.md 产品决定）。

但吵架场景的双盲是**真需求**：

> 如果她先写了我看了，我就会不自觉地回应她的话，
> 而不是说出我真正想说的。写出来的就不是感受，是辩解。

双盲保证两个人写的是**独立**的真实感受。这是这个功能唯一必须做对的地方。

## 二、调研结论（这一节改变了设计）

### 发现 ①：20 分钟是生理下限，不是随便定的

Gottman 把吵架时的状态叫 **情绪淹没（flooding）**：心率超过 100 bpm、思维收窄、
无法接收新信息、共情能力暂时离线。此时**任何有效沟通都不可能发生**。

> 身体代谢掉血液里循环的压力激素，需要**至少 20 分钟**。
> 人们常取的那个 5 分钟、10 分钟休息，几乎从来不够。

**→ 设计改变**：默认 **20 分钟**，并在 UI 上写明理由。
10 分钟作为「还不太严重」的选项保留，但标注它可能不够。

来源：[Emotional Flooding](https://www.connectedcouples.app/blog/emotional-flooding)、
[Why Arguments Make You Shut Down](https://www.reachlink.com/advice/anger/emotional-flooding)

### 发现 ②：冷静与冷暴力只差三件事（**最重要**）

这是最大的风险：**做不好，这个功能会变成冷暴力的工具**。临床给出的区分标准很清晰：

| | 主动暂停（健康） | 冷暴力（伤害） |
|---|---|---|
| 有没有交代 | **说明原因 + 约定多久** | 只丢下一句「随便你」 |
| 有没有归期 | **承诺回来谈** | 无期限 |
| 出发点 | 冷静下来修复关系 | 逃避、惩罚、控制 |
| 对方感受 | 难受，但知道对话还在 | 恐惧、反复自责 |

还有一条直接决定产品形态的研究结论：

> **单方面停止沟通只会激怒对方、导致冲突升级；
> 但双方一起协商暂停的规则和时间，能有效解决大部分冲突，
> 并且一年后有明显的关系满意度提升。**

**→ 设计改变（三处）**：
1. 发起时**必须「有交代」**：约定多久（倒计时可见）+ 一句为什么
2. **必须让对方参与确认**，不能单方面宣布
3. **把「回来」变成产品默认动作**：倒计时结束时界面明确提示「时间到了，可以聊聊了」

来源：[The Importance of Time-Outs in Relationships](https://www.claudiabehnkepsychotherapy.co.uk/post/the-importance-of-time-outs-in-relationships)、
[那些一吵架就冷暴力的人](https://zhuanlan.zhihu.com/p/1970086752501863522)

### 发现 ③：复盘有临床标准流程，照它来

Gottman 的 **Aftermath of a Fight（冲突善后）五步法**：

| 步骤 | 做什么 | 做不做进小程序 |
|---|---|---|
| 1. **Feelings** | 说感受，**但先不说为什么** | ✅ 核心（双盲写感受） |
| 2. **Realities** | 各自描述自己的「现实」，像记者一样 | ✅ 并入感受（第二栏，可选） |
| 3. **Triggers** | 什么旧经历让这事升级 | ❌ **刻意不做**（见下） |
| 4. **Responsibility** | 承认自己那部分责任 | ✅ 做 —— 对治「防御」 |
| 5. **Constructive Plans** | 一起定一个「下次怎么更好」 | ✅ 核心（规矩本） |

第 1 步那句「**说感受，但先别说为什么**」是关键 —— 一说为什么就变成辩解和指责，
这正是双盲要保护的东西。

第 4 步有硬依据：Gottman「四骑士」里 **防御（拒绝承担责任）**
是预测关系破裂的信号之一。让双方各自认领责任，是对它的直接解药。

来源：[Aftermath of a Fight (PDF)](https://northbrisbanepsychologists.com.au/wp-content/uploads/2020/05/Aftermath-of-a-Fight-or-Regrettable-Incident.pdf)、
[Gottman 四骑士](https://thecouplescenter.org/what-are-gottmans-four-horsemen)

### 发现 ④：超过 3 天就不是冷静了

> 健康的暂停通常在**几小时内**恢复对话。冷战超过 **3 天**，
> 已经不是「消化情绪」，而是「心理筑墙」，修复成本随天数上升。

**→ 设计改变**：进情绪页时，对搁置过久的记录显示一句温和提示。
不做推送（小程序没有真后台推送），只在用户主动进来时提醒。

来源：[每次吵架就冷戰？心理師專文](https://www.lunpsy.com/blog/invitation-love-conflict-silent-treatment)

## 三、功能需求

### 状态机

```
inviting ──对方确认──> cooling ──时间到/双方缓好──> feeling
   │                     │                          │
   │                     │                          └─双方都写─> owning
   │                     │                                        │
   │                     │                                        └─双方都写─> planning
   │                     │                                                      │
   └──任一方放弃──> dropped <──任一方放弃────────────────────────────────────────┘
                                                                                │
                                                              双方都写─> done ──┘
```

**status 不靠人手动改** —— 由 `deriveStatus()` 从原始事实（谁确认了、谁写了什么、
时间到没到）算出来，每次操作后重算一次。这样不会出现状态漂移。

### A. 发起冷静（必须「有交代」）

- 显眼按钮：「我们现在需要缓一缓」
- 选时长：**20 分钟（推荐，默认）/ 10 / 30 / 60**
  - UI 写明推荐理由：「身体平复下来至少要 20 分钟」
- 写一句「为什么」—— 这是区分「暂停」与「冷暴力」的关键凭据，
  **允许留空**（有时候就是说不清，强制填会让人干脆不发起）

### B. 等对方确认（调研发现 ② 的直接产物）

- 对方看到：「她想缓一缓 · 20 分钟」+ 原因（如果写了）
- 对方三个选择：
  - **「好，我等你」** → 进入 cooling
  - **「我也需要缓一缓」** → 一起进入 cooling，倒计时从此刻算
  - **「现在就想说清楚」** → 记录对方意愿，**但不阻止冷静**
    （不能一方锁住另一方；只是让发起方知道对方不想拖）

### C. 冷静中

- 双方都看到倒计时（本地 `Date.now()` 减出来）
- 各自可点「我缓好了」：双方都点 → 提前进入复盘；只有一方点 → 「她还在缓一缓」
- 时间到 → **界面明确提示「时间到了，可以聊聊了」**
- 任一方可「这次先算了」（drop）

### D. 写感受（双盲，Gottman 第 1+2 步）

- 提示语明确写：**「先只说感受，不用解释为什么」**
- 两栏：`我的感受`（必填）、`我这边看到的情况`（可选，对应 Realities）
- 写完只拿回执，看不到对方的
- 双方都写了 → 同时解锁，互相可见

### E. 各自的责任（双盲，Gottman 第 4 步）

- 解锁后看到双方感受，然后各自写**「这次我这边有哪里做得不好」**
- 同样双盲（避免看到对方写的之后"对着抄"）
- 双方都写了 → 进入下一步

### F. 下次怎么办（双盲，Gottman 第 5 步）

- 各自提一条**「下次我们可以怎么更好」**
- 双方都提了 → status=done，进规矩本

### G. 规矩本

- 累积每次的「下次怎么办」，成为**我们家的规矩**
- 例如：「晚上 11 点后不谈钱的事」「吵架不翻旧账」

### H. 历史

- 列表：日期、持续多久、走到哪一步、是否完成
- **不记录吵架内容**（原因与感受正文都不进历史）
- 搁置过久的记录给温和提示（调研发现 ④）

## 四、关键设计决策（含「不做什么」）

### ① 冷静期是软约束，绝不锁任何东西

这个小程序没有聊天功能，吵架发生在微信里，所以冷静期不需要（也无法）拦截消息。
它的真正作用是**心理契约**。

**硬拦截是危险的** —— 会变成冷暴力工具（一方锁住另一方）。
调研结论明确：单方暂停激怒对方，**协商式暂停才有效**。
所以产品必须保证双方都能动、都能退出、都能放弃。

### ② 存 deadline，不用 setInterval

数据库只存 `deadline` 时间戳，进页面用 `Date.now()` 减出来，退出再进来依然准确。
`setInterval` 只用于界面刷新（让数字动起来），`onHide` 时清掉 —— 它不影响正确性。

这条在原型阶段就写死了（`prototype/flow-data.html` 的「三条提醒」第 ① 条）。

### ③ 双盲判定在服务端

未解锁时，云函数**只返回自己的内容**，对方的文字在服务端就被丢掉，不在响应里。
与「时间胶囊」同一套思路：把判断放服务端，前端只显示服务端允许它显示的东西。

常见错法是「内容发给前端 + CSS 遮罩」，那种锁抓个包就穿了。

### ④ 不记录吵架内容

「为什么」和感受正文只在**本次流程期间**可见，归档后不再返回。
历史只留日期、时长、进度。

理由：记录内容 = 以后可以翻旧账 = 更伤感情。复盘的价值在「我们学到了什么」，
不在「你上次也是这么说的」。

### ⑤ 刻意不做 Triggers（触发点）

Gottman 第 3 步是「什么旧经历让这事升级」。**不做**：

- 自用产品，两个人的旧账彼此都清楚，写出来就是二次伤害
- 这是五步里最容易变成「翻旧账」的一步
- 专业咨询师在场时才适合做

**做减法也是设计**：五步做四步，砍掉最容易伤人的那一步。

### ⑥ 每一步都要双方完成才解锁下一步

避免单方面宣布。单方点「完成了」不算数 —— 那等于「我单方面宣布没事了」，
比吵架更伤人。

## 五、技术计划

### 数据模型

集合 `cools`（一次冷静 = 一条记录）：

```js
{
  _id,
  pairId,                    // 分区，和其他集合一致
  by,                        // 谁发起的
  reason: '',                // 为什么（可空；仅流程期间可见，不进历史）
  minutes: 20,               // 选的时长
  startedAt: 1758720600000,  // 发起时间戳
  deadline: 1758721800000,   // ★ 倒计时的唯一依据
  accepted: [openid],        // 谁确认了（含发起人自己）
  partnerWanted: '',         // 对方选了「现在就想说清楚」时记录
  ready: [openid],           // 谁点了「我缓好了」
  feelings: [{ by, name, text, view, at }],   // 感受 + 我看到的情况
  owns:     [{ by, name, text, at }],         // 各自的责任
  plans:    [{ by, name, text, at }],         // 下次怎么办
  status: 'inviting'|'cooling'|'feeling'|'owning'|'planning'|'done'|'dropped',
  active: true,              // 是否还需要处理（供首页查询）
  droppedBy: '', droppedAt: 0,
  doneAt: 0,
  createdAt
}
```

### 状态推导（唯一真相）

```js
function deriveStatus(c, now) {
  if (c.droppedBy) return 'dropped'
  const members = c.memberCount || 2
  if ((c.accepted || []).length < members) return 'inviting'
  if (now < c.deadline && (c.ready || []).length < members) return 'cooling'
  if ((c.feelings || []).length < members) return 'feeling'
  if ((c.owns || []).length < members) return 'owning'
  if ((c.plans || []).length < members) return 'planning'
  return 'done'
}
```

单人（未配对）时 `memberCount = 1`，流程自动简化成"一个人走完"。

### 云函数 `mood`

| action | 作用 | 关键约束 |
|---|---|---|
| `current` | 取进行中的冷静（含倒计时剩余毫秒） | 未解锁时只返回自己的内容 |
| `start` | 发起冷静 | 同一 pair 只能有一条 active |
| `accept` | 对方确认（好/一起缓/现在就说） | 双方确认后才进 cooling |
| `ready` | 我缓好了 | 双方都 ready → 提前进复盘 |
| `drop` | 放弃这次 | 任一方可放弃 |
| `feel` | 写感受 + 我看到的情况 | 双盲；双方都写 → 解锁 |
| `own` | 写我这边的问题 | 双盲 |
| `plan` | 写下次怎么办 | 双盲；双方都写 → done |
| `history` | 历史 + 规矩本 | **不返回 reason 和 feelings 正文** |

**双盲实现**（`current` / `history` 都适用）：

```js
const n = (c.feelings || []).length
const mine = (c.feelings || []).filter(f => f.by === OPENID)
return { feelings: n >= members ? c.feelings : mine }
```

### 页面 `pages/mood/mood`

替换占位页。按 status 渲染不同区块：

1. `inviting` — 显示「她在等你的回应」+ 三个选择
2. `cooling` — 大倒计时 + 双方状态 + 「我缓好了」
3. `feeling` — 感受输入（双盲）+ 已解锁时显示双方感受
4. `owning` — 责任输入（双盲）
5. `planning` — 下次怎么办（双盲）
6. `done` — 完成态 + 规矩本入口
7. 无进行中 — 发起按钮 + 规矩本 + 历史

### 首页入口

`home` 增加 cools 查询，返回 `cooling: { status, minutesLeft }`，
首页顶部显示提示条（「冷静中 · 还有 12 分钟」）。用和 `reminds` 相同的模式
（`field()` 限定字段 + `catch()` 兜底，表没建也不影响首页）。
