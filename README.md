### 2.6.0 骰盅 + 全联机（2026-10-08）

用户要求两条：
1. 「摇骰子的动画效果和真实场景还是差很多，还有音效，尽量做到和现实差不多的感觉」
2. 「除了多人联机，其他单机的几乎没用，删除都可以。全部都是在线多人玩的」

#### 一、补上「骰盅」—— 这是"不像现实"的根源

对着真实现场逐条比对，发现缺的正是**盅**：

| 现实 | 改造前 |
|---|---|
| ① 骰子落进盅里，几声脆响 | 无 |
| ② 握住盅上下摇，骰子在**盅内**乱撞 | 骰子在"空中"翻 |
| ③ **"咚"一声扣在桌上** | 完全没有这一下 |
| ④ 提起盅，骰子露出来 | 直接显示点数 |

**关键认识：现实里摇盅时根本看不见骰子**（盅不透明）——
悬念恰恰来自"看不见"。改造前让骰子在空中翻滚，所以看着假。
**盅不是装饰，它是这个游戏的核心道具**：挡住骰子制造悬念、扣盅那一声是仪式感顶点、揭盅是悬念释放。

现在的完整流程（每一步都有对应的声音、动画、震动）：

```
骰子入盅 → 摇盅(1.05s) → 扣盅(整屏震) → 揭盅 → 骰子在桌上滚两下才停
```

**大话骰：扣盅后才能看自己的骰子**（用户明确要求）。
做成**按住才看**（松手立刻扣回），而不是点一下切换 ——
按住的交互本身就复刻了"偷偷瞄一眼"的动作。没看过骰子不给叫骰。

#### 二、骰盅是渲染出来的，不是画的

`scripts/render-cup.py`（22 秒出 3 张，共 84 KB），复用骰子的渲染器：
同一套 SDF + 光线步进 + 光照。**两个物体必须同一套光照**，
否则叠在一起时明暗对不上，一眼假。

三态：`cup-down`（扣着）/ `cup-shake`（摇动）/ `cup-up`（提起）。

⚠️ **SDF 写错的典型症状是"放射状尖刺 + 形状不对"**：
第一版用了"任意朝向圆台"的通用公式，我把它翻译错了，
返回值不再是真实距离（违反 SDF 的 Lipschitz 条件），
光线步进的步长 overshoot，画面出现放射状尖刺、形状塌成圆顶。
**看到"尖刺 + 形状不对"要先怀疑距离函数本身**，而不是光照或步进参数。
换成轴对齐版本（三行、易验证）后正常。

另一个坑：盅的**比例**。第一版"高 0.84 / 底径 1.2"（高只有底径的 0.7 倍），
渲染出来是个矮胖墩子，像茶杯盖。真实骰盅的高 ≈ 底径的 1.3 倍。

#### 三、音效按现实拆成五声

新增 5 个（`scripts/gen-audio.py`，纯代码合成）：

| 音效 | 对应现实 |
|---|---|
| `dice-into-cup` | ① 骰子入盅 —— 3~4 声**间隔递减、响度递减**的脆响（真实弹跳） |
| `cup-shake` | ② 摇盅 —— 带 **3.5Hz 手摇起伏**（★ 见下） |
| `cup-slam` | ③ ★ 扣盅 —— 口沿撞桌 + 桌面"咚" + **盅内骰子被震跳一下** |
| `cup-lift` | ④ 揭盅 —— 口沿离桌的摩擦吸附声 |
| `dice-on-table` | ⑤ 骰子在桌上滚两下才停（间隔 1.35 倍递增） |

**★ 摇盅必须叠"手摇起伏"**：第一版做成均匀的密集撞击，
听起来像下雨而不像摇盅 —— 因为真实的摇动是**有节奏的往复**（约 3.5Hz）。
加上响度起伏（谷值压到 0.45）之后才像。这是最像/最不像的分界线。

**★ 扣盅里"骰子在盅内被震得跳一下"是真实物理**：
空盅扣下去没有这一下。加上它立刻有了"里面有东西"的实感（延迟 55ms 与 108ms 两声）。

震动分级（有断言锁着）：
- 扣盅 → `medium`（一局里的重音）
- **摇盅 → 不震**（持续 1 秒的过程，震了整局嗡嗡响，用户会直接关掉）

### 2.5.0 骰子改成真 3D 渲染（2026-10-08）

**一句话**：骰子不再用 CSS 拼，改成离线渲染的 PNG —— 因为**圆角立方体在 CSS 里数学上无解**。

#### 为什么必须换掉 CSS 方案

上一版（2.4.0）的骰子是用三块面 skew 拼的等轴测。试了四种方案，全部有硬伤：

| 方案 | 结果 |
|---|---|
| ① 三块等宽矩形拼立体 | 不是透视投影，像"盒子上盖了块案板" |
| ② clip-path 切平行四边形 | 几何对了，但面是锐边，没有圆角 |
| ③ 真 3D 立方体（6 面 + preserve-3d） | 能翻滚，但**棱和角做不出圆角**：加 border-radius 角上露缝、加 border 棱上出双线、让面放大重叠变成"枕头状鼓包" |
| ④ 等轴测 2D（三块面 skew） | 能看，但 **skew 会连带扭曲圆角** —— 圆角永远不是正圆，放大看是斜椭圆 |

**根本原因（记住这条，别再回头试 CSS）**：
CSS 的变换全是**仿射变换**。仿射变换保持"平行"，但**不保持"圆"** ——
所以任何"先画直角矩形再斜切"的路子，圆角必然跟着变形。
而 CSS 3D 的每个面在数学上是锐边，6 个面拼不出连续曲面。
→ **在 CSS 里做真实圆角立方体，数学上无解。**

#### 现在的做法：`scripts/render-dice.py`

自己写了个离线渲染器：

- **SDF（有符号距离场）**描述几何 —— 圆角立方体（rounded box SDF）**布尔减**球形点数
- **光线步进**求交，法线由中心差分梯度算出
- **物理光照**：主光 + 补光 + 底部反弹光 + Blinn 高光 + 边缘光 + AO（环境遮蔽）
- 输出 6 张带透明通道的 PNG（点数 1~6），约 **165 KB**

```bash
python3 scripts/render-dice.py            # 约 1 分 50 秒，渲染 6 张
python3 scripts/render-dice.py --size 600 --colors 64
```

产物是**提交进仓库**的：别人 clone 后不需要跑脚本也能直接用。

#### 三个必须记住的技术点

**① 点数必须填深色，不能只做凹坑。**
坑壁受光会在凹陷周围形成一圈亮环，坑内若与表面同色，人眼会把它读成
**"凸起的白珍珠"**而不是"凹坑" —— 这是光照歧义，同一种明暗分布既能解释成凹也能解释成凸。
真实骰子的点数是填色的；填色同时消除歧义，也让小尺寸下点数可读
（游戏里骰子只显示约 133pt，纯凹坑在那个尺寸下会糊成一片）。
配套还要**抑制坑内的高光与边缘光** —— 高光是凸面才有的特征，坑底出现亮点就又读回凸起了。

**② alpha 边缘必须做颜色外扩（bleed），否则暗面旁边会有一圈发白的描边。**
未命中的背景像素如果统一填亮色（骨白），那么骰子**暗面**（底部/右侧）的边缘
抗锯齿像素就会按比例混入亮色 —— 合成到深色桌面上就是一圈锯齿白边。
正确做法：让每个半透明像素的 RGB 取**离它最近的真实表面颜色**，alpha 不变。
代码里是 `bleed_edges()`。

**③ 光照配比是按"实测三个面亮度"标定的，不是拍脑袋填的。**
第一版 `key .95 / fill .30 / bounce .16 / 环境 .10`，实测：

| 面 | 第一版 | 现在 | 真实骰子参考 |
|---|---|---|---|
| 顶面（亮） | 236 | 249 | ≈240 |
| 正面（中） | 151 | 201 | ≈205 |
| 右面（暗） | 108 | 160 | ≈155 |

第一版暗面 108 太黑（白色塑料骰子的暗面约 150），整颗骰子"发灰发脏"。
而且**补光方位错了**：它正对着右面，一调大就把右面照得比正面还亮，明暗层次整个反过来。
现在补光挪到右侧偏后，环境光从 0.10 提到 0.34。

#### 修掉的两个渲染器 bug（都很隐蔽）

**bug 1：SDF 平滑布尔减的公式写错了 —— 渲染出来是**全透明**。**
smooth max 必须用 `(a - b)`，代码里写成了 `(a + b)`：

```python
# ✗ 错：h = clip(0.5 - 0.5 * (a + b) / k)
# ✓ 对：h = clip(0.5 - 0.5 * (a - b) / k)
```

用 `(a+b)` 时，只要 `|b| > a`（**背面那些看不见的点数球恰好是这种情况**），
`h` 就被钳到 1，函数直接返回球的距离（约 -3.37），于是"立方体外部"被判成"内部"：
光线第一步就"命中"，`t` 停在 0，**整张图 alpha 全 0**。
症状极具误导性 —— 看起来像"渲染器没跑"，其实是跑了但全错（每张 PNG 1298 字节，全是透明）。

**bug 2：光线步进的退出条件 `hit.all()` 永远为假 → 每帧跑满 80 轮。**
骰子只占画面一部分，**背景像素永远不会命中**，所以 `hit.all()` 永远不成立，
80 轮循环一次不落地全跑完；而且已命中/已逃逸的像素之后每轮还在重复求值。
改成"每轮只对仍活跃的像素求值 + 活跃集合空掉就退出"后，
单面从 **229 秒降到约 19 秒**（另加了包围盒裁剪，省掉 52% 空白像素）。

#### 顺手做的优化

- **只对朝向相机的 3 个面求 SDF**：被剔除的 3 个面的点数球完全埋在立方体内部，
  对可见表面**精确无影响**（不是近似），每次求值的球数 21 → 6
- **裁剪到包围盒**：省掉 52% 的空白像素
- **调色板量化到 64 色**：240 KB → 165 KB，实测平均色差 **0.55/255**（肉眼不可辨）

> 为什么不用 WebP（同质量只要 41 KB）：小程序 `image` 组件对 WebP 的支持
> 依赖基础库与系统版本，万一不显示就是**骰子整个消失** —— 这是游戏的主角元素，不值得赌。

#### 新增的回归防线

`scripts/test-contract.js` 加了 **2 项断言**（字段契约 14 → 16 项）：

- **③d 模板引用的图片文件必须存在** —— `<image>` 在文件缺失时**静默不显示**，
  不报错、不警告，骰子直接消失，而 `check.sh` 和其它断言都发现不了
- **骰子图 1~6 必须六张齐全** —— 缺哪个点数，哪颗骰子就不显示

两条都做过**反向验证**（临时移走 dice-4.png → 确实报错；把路径改成 `diceX-` → 确实报错），
不是摆设。

### 2.3.0 动画与音效升级（2026-10-08）

用户要求：「丰富一下，动画和音效是否丰富，要达到腾讯工作室开发的游戏标准」。

**做之前先诚实评估了差距**：原来 22 个关键帧大多是简单 fade/slide，
25 个音效都是单层合成。腾讯工作室标准的关键要素缺这些 ——
预备动作、跟随动作、屏幕震动、音高随机化、分层音效、时序编排。
逐项补齐。

**音效：25 → 30 个，全部纯代码合成（不下载任何素材，版权干净）**

新增的都是"分层"的 —— 商业游戏的一个事件由多轨叠出来：

| 音效 | 层次 |
|---|---|
| `reveal-hit` 揭晓重击 | 高频明亮层 + 低频冲击层 + 金属尾音（三层） |
| `shaker-metal` 金属骰盅 | 高频正弦 + 不谐和泛音（金属感） |
| `dice-tumble-wood` 木质骰子 | 二阶低通噪声 + 低频腔体共鸣（和金属形成**2.1 倍频差**的质感对比） |
| `confetti` 撒花 | 9 个快速上行短音 + 纸屑沙沙声 |
| `charge-up` 蓄力 | 扫频渐强 + 8Hz 颤音（紧张感） |
| `fail-drop` 失败下坠 | 连续滑音 + 落地冲击 |
| `combo-1..4` 连击 | 音高逐级升高（E5→G5→B5→D6） |
| `pour`/`clink`/`gulp` | 倒酒 → 碰杯 → 咽下（把一个动作拆成三步声音） |

**音高随机化**：每次播放给 ±4% 播放速率抖动。同一音效连播几十次
（骰子连撞、转盘咔哒）如果每次一模一样，耳朵立刻听出"这是采样循环"。
连击音例外（音高是设计的一部分，固定）。

**关键帧：22 → 55 个（游戏部分），补齐商业动效的四个要素**

| 要素 | 实现 |
|---|---|
| **预备动作** | 骰子落定前先向上提 30rpx 再砸下（直接砸显得轻飘） |
| **跟随动作** | 落地回弹、结果弹层过冲、光条扫过 |
| **打击感** | 骰子落定 / 转盘停稳 / 开盅时**整屏震动**（只有元素动、背景不动是飘的） |
| **时序编排** | 大厅标题→卡片逐张→提示，按 0.1s 间隔入场；玩家列表逐个滑入 |

**多人游戏补了一个真功能：开局倒计时**
骰子已经生成好，但玩家还在看别人的名字、还没把手机放好 ——
直接开局 = 有人错过第一轮叫骰。3 秒缓冲 + 读秒声（最后一声更急促），
云函数没定时器，靠轮询触发自动推进。

**另一处真功能：连庄（streak）**

### 2.0.0 情绪与冷静期（v2 唯一功能项）

**吵架时的「暂停键」，和好后的「复盘本」。**
完整需求与调研见 `docs/v2-情绪冷静期.md`。

动手前查了 Gottman 研究所与临床实践的资料，**四条发现直接改进了设计**：

| 发现 | 对设计的影响 |
|---|---|
| 情绪淹没（flooding）后心率 >100 bpm，身体代谢压力激素**至少需要 20 分钟** | 默认时长定为 20 分钟，UI 上写明理由（5/10 分钟那种休息几乎从来不够） |
| **单方暂停会激怒对方，双方协商的暂停才有效** | 发起必须对方确认才能开始倒计时；任一方随时能放弃 |
| 冷静与冷暴力只差三件事：**说明原因、约定多久、承诺回来** | 「为什么」字段是区分二者的凭据；倒计时结束明确提示「可以聊聊了」 |
| Gottman「冲突善后五步法」是临床标准流程 | 复盘按它做：感受（含"我看到的情况"）→ 各自的责任 → 下次怎么办 |

**做减法**：五步法里的第 3 步 Triggers（什么旧经历让这事升级）**刻意不做** ——
自用产品里那是二次伤害，也是最容易变成「翻旧账」的一步。

**三个命门**（都有断言覆盖）：

1. **双盲**：未解锁时对方的文字在服务端就被丢掉，不在响应里。
   理由：她先写了我看了，我就会不自觉地回应她的话，写出来的就不是感受，是辩解。
2. **deadline 而非定时器**：退出小程序再进来，倒计时依然准确。
   `setInterval` 只用于界面走秒，`onHide` 清掉，它停了也不影响正确性。
3. **绝不锁人**：发起要确认、任一方可放弃、不阻止对方说话。
   做不好，这个功能会变成冷暴力的工具。

**历史不记吵架内容** —— 只留日期、时长、走到哪一步。
记录内容 = 以后可以翻旧账 = 更伤感情。

顺带：`home` 增加冷静摘要查询（首页顶部提示条），`initdb` 集合 5 → 6。

### 1.5.2 的工程修复：derive.js 同步漏洞（**这条比上面所有 UI 问题都重要**）

`derive.js` 是「全 App 唯一的时间算法源」，云函数独立打包不能跨目录 require，所以每个用它的
云函数都留一份拷贝。**当时实际有 6 处**（prototype + miniprogram/utils + daily/home/chronicle/reminds），
但旧版 `scripts/sync-derive.sh` **硬编码了 2 条路径**，`check.sh` 也只校验这 2 处。

结果：`home` 和 `chronicle` 的拷贝长期停在旧版，**少了 `clampDay`** ——
那个函数正是为了修「每月 31 号在 9 月会静默进位成 10.01」而加的。

这两个云函数目前只调 `derive()`（不含月滚动），所以**还没炸**；但只要以后有人在 `home` 里
调一次 `nextMonthly`，就会拿到错误日期，而且没有任何测试会拦住它。

修法：`sync-derive.sh` 改成自动扫描 `cloudfunctions/*/derive.js`，以后新增云函数自动纳入。
现在 `check.sh` 会校验全部拷贝 —— 1.5.3 删掉 `daily` 后是 **5 处**，输出 `derive.js 5 处一致 ✓`。

### 一条重要的产品决定：去掉了「每日一题」

原本的形态是每天推一道题、两人分开作答、都写完才解锁。**这个设计被否掉了**，理由是：

> 每日一问是热恋期产品的套路，靠制造新鲜感让人天天打开。
> 但在一起两年多以后，真正会让人打开小程序的时刻是「今天有件事想记下来」，
> 而不是「今天又有一道题要做」。
> 每天被问一个问题，三天后就会变成一条未读红点带来的愧疚感。

改成了 **随手记（moments）**：

- 没有"今天"的概念，没有连续打卡，没有补卡 —— 想记就记
- 写完她立刻能看见（不再双盲 —— 双盲是答题的规则，不是记录的规则）
- 一条也算数，不再要求"两个人都写了才显示"
- 一个人也能先用（不用等她加入才敢动笔）

### 1.5.1 新增两个功能（2026-09-23）

**① 时间胶囊** —— 写给未来的信

核心不是"能写信"，是**到期之前谁都打不开**：

- 未到期的信，云函数用 `field()` 明确**不查 text 字段** —— 正文根本没离开数据库
- 接口返回里 `text: null`，整个响应搜不到正文的任何一个字（有断言验证）
- 已到期的信不能删 —— 那是"已经寄出的信"，删了等于篡改历史
- 到期后可以回信，形成来回

> 和「双盲解锁」是同一套思路：把判断放服务端，前端只显示服务端允许它显示的东西。
> 常见错法是"内容发给前端 + CSS 遮罩"，那种锁抓个包就穿了。

**② 要记得的事** —— 生日 / 纪念日 / 还款

难点在两个地方：

- **提前量**：生日当天才提醒等于没提醒（那天你已经在饭桌上了）。
  每条带 `leadDays`，进窗口就标红说"该准备了"，而不是干巴巴一个数字。
- **日期滚动**：三种重复方式的边界各不相同，全部有断言覆盖：
  - 每年：`2/29` 在平年回落到 `2/28`，不能跳到 3/1
  - 每月：`31 号` 在小月落到月末（**这里抓到一个真 bug**：9 月会算成 10.01）
  - 一次：过了就是过了，不再滚动

还带一个「上次送了什么」字段 —— 解决连送三年同款的真实问题。

### 1.4.0 提速（用户反馈"加载慢、反应慢"）

**根因**：首页每次打开**串行**调 5 个云函数：

```
pair(status) → moments(list) → moments(stats) → chronicle(list) → daily
```

每次往返 200~600ms，串行相加 1~3 秒，而且 5 个函数各自可能冷启动。

**三层修法**：

| 层 | 做法 | 效果 |
|---|---|---|
| ① 聚合 | 新建 `home` 云函数，服务端内部 `Promise.all` 并发查完再一起返回 | **5 次往返 → 1 次** |
| ② 缓存 | 三个 tab 页加本地缓存：先用上次数据铺满界面，云端数据回来再静默替换 | 打开即见内容，不是白屏 |
| ③ 并发 | 编年史页的 list + stats 从串行改并发；其余页面同样处理 | 各页面少等一次往返 |

**一个细节**：缓存里的天数不能直接用 —— 它是昨天存的。
所以 `applyCache()` 会拿缓存里的 `anniversary` 在本地 `derive()` 重算一次天数，
保证即使走缓存，显示的也是**今天的真实天数**（实测跨零点后自动从 910 变成 911）。

### ⚠️ 改完代码一定要部署云函数（2026-10-08 踩坑）

**症状**：点「开房间」报 `Error: no baseresponse`，或某个功能"点了没反应"。

### 关于 `answers` 的唯一索引（1.5.3 已作废）

历史遗留：`answers` 是旧版「今日一题」的表，已被 `moments` 取代。
1.5.3 删掉了 `daily` / `answer` 云函数与 `initdb` 里的题库种子，
所以那条唯一索引**再也不需要建了** —— 直接在控制台把 `questions` / `answers` /
`pings` / `foods` 四张空表删掉即可。

### 关于 bootstrap 这个函数

微信 CLI **没有调用云函数的命令**，`initdb` 只能人工去控制台点。为了让它能自动跑，
加了一个 `bootstrap` 云函数：云函数之间可以互相 `callFunction`，所以由它在云端替你调 `initdb`。
小程序启动时会先调 `bootstrap`，**跑完弹窗告诉你建了几个集合**。

## 二、第一次部署的 6 步（换 AppID 时才需要）

### 第 1 步：注册小程序，拿 AppID

1. 打开 <https://mp.weixin.qq.com> → 立即注册 → **小程序**
2. 主体类型选 **个人**（不需要营业执照）
3. 用一个**没注册过公众号/小程序**的邮箱
4. 注册完：登录后台 → 左侧「开发管理」→「开发设置」→ 复制 **AppID(小程序ID)**

> 个人主体能用的能力：云开发 ✅、内容安全接口 ✅、分享 ✅
> 个人主体**不能**用：微信支付 ❌（所以 v1 不做任何收费功能，这和之前说的一致）

### 第 2 步：装开发者工具

下载稳定版：<https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html>

### 第 3 步：导入工程

1. 开发者工具 → 导入项目
2. **目录**选到 `情侣小程序/`（就是有 `project.config.json` 的这一层）
3. **AppID** 填第 1 步复制的那个
4. 后端服务选「**微信云开发**」
5. 导入后如果提示 AppID 不一致，点「确定」覆盖即可

### 第 4 步：开通云开发

1. 工具顶部点「**云开发**」按钮
2. 开通 → 环境名随便填（比如 `xiaowo`）→ 套餐选 **基础版 1**（免费额度足够两个人用）
3. 开通后左上角能看到**环境 ID**，形如 `xiaowo-3g8a1b2c3`
4. 把它填进 `miniprogram/config.js` 的 `env` 字段：

```js
module.exports = {
  env: 'xiaowo-3g8a1b2c3',   // ← 换成你的
  ...
}
```

> 只有一个环境时留空也能跑。填上更保险。

### 第 5 步：部署云函数

在工具左侧文件树里，**右键** `cloudfunctions` 下的每个目录 → 「**上传并部署：云端安装依赖**」。
或者用命令（改了哪个传哪个，`--remote-npm-install` 必须带，否则 `wx-server-sdk` 装不上）：

```bash
CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli
for fn in pair moments home chronicle wishes capsule reminds initdb bootstrap; do
  $CLI cloud functions deploy --project "$(pwd)" --env <环境ID> \
    --names "$fn" --paths "$(pwd)/cloudfunctions/$fn" --remote-npm-install true
done
```

### 第 6 步：建库

云开发控制台 → 「云函数」→ `initdb` → 「测试」→ 参数留空 `{}` → 运行。
返回里会列出 11 个集合已创建、20 道题已灌入。

其实不用手工跑：小程序启动时会先调 `bootstrap`，由它在云端替你调 `initdb`。
`app.js` 里的 `DB_VERSION`（当前 `4`）控制这件事 —— **以后再加集合，只要把这个数加一**，
所有设备下次启动自动补建，不用教用户清缓存。

## 四、常见问题

**「云函数 pair 还没部署，或云环境不对」**
→ 第 5 步没做，或 `config.js` 里 `env` 填错了。

**数据都是空的**
→ 正常。云端集合建好了但都是 0 条 —— 这是干净状态，不是坏了。

**她扫不到 / 打不开**
→ 开发版只有**开发者本人 + 体验成员**能打开。后台「成员管理 → 体验成员」把她的微信加进去。

**想改在一起的日子**
→ 设置页改。全 App 只有这一个入口，改完所有数字自动跟着变。

│       ├── pair/            配对
│       ├── settings/        设置（唯一的时间输入口）
│       ├── capsule/         时间胶囊
│       └── reminds/         要记得的事
├── cloudfunctions/          10 个
│   ├── pair      配对 / 状态 / 设置
│   ├── moments   随手记
│   ├── chronicle 编年史（数据源是 moments）
│   ├── wishes    想去·去过

├── scripts/
│   ├── check.sh             语法 + WXML + 页面齐全 + derive 一致（全部 5 处）
│   ├── test-mood.js         情绪·冷静期：双盲 / deadline / 不锁人

**一条纪律**：`derive.js` 有 **5 处拷贝**（`prototype/` 是源，另有 `miniprogram/utils/` 和

改算法**只能改 `prototype/derive.js`**，然后跑 `./scripts/sync-derive.sh` 同步全部拷贝。

> 2026-09-24 修正：这里原来写「三份拷贝」，而同步脚本只硬编码了 2 条路径，
> 导致 `home` / `chronicle` 长期停在旧版（少了 `clampDay`）。现在脚本自动扫描，不会再漏。
